RecoverAI

Automated payment failure recovery for Razorpay merchants. Classifies failures, picks the right action, sends a localized message. No LLM in the transaction path.

Who built this

I'm Nikunj. I'm an ML/DL student. I built this because I looked at how payment failures are handled today and thought: this is a solved classification problem being treated as a customer service problem.

When a payment fails, the error code already tells you what went wrong. A UPI timeout is not the same as a stolen card. But most systems treat them identically: wait 3 days, send a generic email, hope the customer comes back. That's not recovery. That's resignation.

The problem

Failed payments are not lost customers. They are recoverable revenue stuck behind two kinds of friction:

  • Infrastructure friction — bank timeouts, gateway errors, UPI node downtime. These are transient. Retry in 30 minutes and they usually succeed.
  • Liquidity friction — insufficient funds, expired cards, declined transactions. These need a different approach: a payment link with an alternative method, or routing to Razorpay PayLater.

Current solutions retry blindly (getting merchants flagged by card networks) or send generic English emails to Hinglish-speaking customers (single-digit open rates).

The hot path is pure Python. No network calls except to Razorpay's own API. The LLM runs offline, reading yesterday's audit logs and rewriting Hinglish templates using behavioral economics nudges. Better templates get picked up by the hot path the next day.

Why it's built this way

Why no LLM in the transaction path?

Three reasons:

  1. Availability. If your LLM provider goes down, your recovery pipeline goes down. Merchants lose money in real-time.
  2. Latency. An API call to Gemini takes 1-4 seconds. RandomForest inference takes <1ms. The webhook response window is tight.
  3. Cost. At Rs 0.01-0.05 per call, 100K daily failures = Rs 1,000-5,000/day. The rules engine costs zero.

Why RandomForest, not deep learning?

The input is tabular: error code, payment method, amount, retry count. Four output categories. For tabular data with discrete features, tree-based models consistently beat neural networks. (Grinsztajn et al., NeurIPS 2022: "Why do tree-based models still outperform deep learning on tabular data?")

Why PayLater instead of micro-credit?

An earlier version offered "just-in-time micro-credit." I removed it. Issuing credit requires an NBFC license under RBI guidelines. Razorpay already has a PayLater product backed by licensed partners. Same outcome, zero regulatory risk.

What actions can the system take?

ActionWhen
retry_paymentTransient failures (timeouts, gateway errors)
send_payment_linkRecoverable failures, alternative payment method
offer_razorpay_paylaterInsufficient funds, high-LTV customer
escalate_to_humanSuspicious activity, exceeded retry limits
no_actionTerminal failures (account closed, fraud flagged)

Any output not in this list is rejected and falls back to escalate_to_human. Enforced in code, not by prompting.

Safety and compliance

  • Bounded actions — hard-coded whitelist. The system cannot hallucinate a refund or issue credit.
  • Escalation chain — retry, then payment link, then PayLater, then human. Cannot be skipped.
  • Stopping rules — max 3 retries, 4-hour cooldown, max 3 customer touchpoints.
  • Suspicious payments — always escalated to human. No automated retry.
  • Audit trail — every decision logged to SQLite with payment_id, action, reasoning, confidence, timestamp.

Limitations

  1. Recovery outcomes are simulated. Razorpay test mode cannot execute real retries.
  2. Classifier uses a lookup table (100% accurate for known codes). A trained ML model would handle ambiguous edge cases better.
  3. SQLite won't scale past ~100 concurrent writes. Production needs PostgreSQL.
  4. Single-process server. Production needs worker processes behind a load balancer.
  5. 70 synthetic training transactions. Production needs thousands of real failure logs.
